# Annotation QA Stress Test

**Purpose:** measure how the portfolio's existing four rule-based QA utilities behave on a deterministic, synthetic 10,000-row workload.

## Scope

This is a bounded engineering/QA exercise, not a production certification. It exercises the current implementations without changing their validation rules:

1. Annotation CSV Validator — validates 10,000 synthetic annotation rows.
2. Annotation Consistency Checker — checks the same 10,000 rows for configured cross-field and cross-record patterns.
3. Annotation QA Dashboard — inspects the same rows and verifies that all rows are loaded and no unexpected issues are reported.
4. AI Response Score Calculator — analyzes 10,000 synthetic evaluation records and renders its summary.

The generator uses a fixed seed. It also checks byte-for-byte repeatability, several negative cases, and SHA-256 hashes before and after processing to detect input mutation.

## Reproducibility

Run from the repository root with Python 3:

```bash
python 16-annotation-qa-stress-test/stress_test.py
```

The script uses only the Python standard library and writes `stress-test-results.json` beside itself. GitHub Actions runs the same command on pushes affecting the portfolio or this workflow.

## What is measured

- Wall-clock elapsed time for each measured Python operation.
- Peak Python memory allocations reported by `tracemalloc`.
- Processed row counts, deterministic generation, negative checks, and input-file integrity.
- Python version and runner platform.

**Memory caveat:** `tracemalloc` does not report process RSS, native allocations, or total machine memory. The reported peak is not a complete memory-footprint measurement. Timings and memory values are specific to the GitHub-hosted runner and should not be treated as universal benchmarks.

## Interpretation limits

- The dataset is synthetic and generated by one script; it is not representative of every client schema or workload.
- 10,000 rows is a useful larger test than the small portfolio samples, but it is not evidence of unlimited scale, sustained throughput, concurrency, or production service-level reliability.
- These tools load rows into memory; this test measures their current behavior rather than proving streaming or bounded-memory processing.
- The consistency checker only flags its configured patterns. No result establishes semantic annotation correctness.
- Passing malformed-input checks means only those exact cases were rejected or reported as expected.
- No independent reviewer, production data, multi-user concurrency, long-duration soak test, or external deployment is involved.

## Results

The committed `stress-test-results.json` is generated by the workflow and records actual measurements from that run. Do not copy its numbers to other environments without preserving the runner context.

## Evidence boundary

A successful run supports this narrow statement: **the four current utilities processed the generated 10,000-row synthetic workload under the recorded GitHub Actions environment, with the listed checks passing.** It does not justify describing the tools as production-ready.
